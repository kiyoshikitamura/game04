## 一括判断案 SBG-01（未承認）

6項目は相互に関連するため、下記を一式として推奨する。素材の採用は既に確定しており再承認対象ではない。

|必要な判断|推奨案|影響・代案|
|---|---|---|
|表示・設定先|本陣の既存背景選択に10点追加|新しい選択画面を増やさず既存Dialogを使用。他画面用とする場合は対象画面・選択方法の追加定義が必要|
|解放タイミング／期間|経路を問わずキャラ本体の初回入手で永続解放|ガチャ・魂からのキャラ解放・正式付与等で同じ判定を再利用。魂を所持しただけではキャラ入手ではない。ガチャ限定等は入手経路識別が追加で必要|
|既所持者|反映後、対応SSRを既に所持するユーザーも解放|保有者への再取得要求を避ける。過去の取得日時を捏造しない。新規入手のみ対象にする場合は既所持者に不利益がある|

## 承認後の具体的な実装案（未実行）

1. 正式キャラID→固定背景ID→配信パスの10件マスターを追加。キャラ名による判定・番号順の旧ID変換はしない。
2. stateへ任意項目`unlockedHomeBackgroundIds?: string[]`を追加し、背景ID集合として永続保持する。旧stateは空集合として安全に読めるようにする。既存`homeBackgroundId`と旧ID互換をそのまま残す。
3. サーバー側で、入手後state.charactersとマスターの一致を調べ、未登録の背景IDだけ集合に追加する。既所持への適用を承認した場合は、state読み出し時に一度だけ同じ同期を実行する。順序を安定化し、差分なし読み出しで不要commitを起こさない。
4. `commit`へ集約できる経路と、独自RPC保存経路（shop等）を確認し、サーバーで解放資格を統一する。G3のガチャも同じ取得後同期関数へ接続する。受取・取得requestIdとstate更新を同じ既存トランザクションに含める。
5. 既存`isHomeBackgroundUnlocked`をstateを含む判定へ拡張し、エリア背景とSSR背景を明示分岐する。UI・API双方で同じ判定を使用し、未知背景ID／未解放選択を拒否する。既存の非area背景を無条件解放する処理へSSRを紛れ込ませない。
6. 既存の`set_home`で選択を保存する。取得による選択変更・通知・報酬を追加しない。永続フラグは将来の状態変動で削除しない。
7. JSON stateへの追加で足りるか既存RPCの許可フィールドを親が確認する。DB列追加は必要が判明した場合だけ行い、全ユーザー資産変換や一括migrationは行わない。

## 限定検証・引継ぎ

- G2承認後：未所持拒否、魂だけでは未解放、SSR本体入手→解放、既所持適用、重複／同一requestId再送、選択非自動変更、set_home保存→API再読込→再ログイン保持を専用QAで確認。
- 既存エリア背景の解放・選択と旧選択IDが維持されることを同じ変更原因の回帰範囲として確認。
- 正規化とID対応が済んでも、解放・選択・保存の本体受入済みとはしない。
- G3：正式ガチャの実入手→G2共通解放処理→選択・再ログインまでを受入。G2のfixture／手動付与試験で代替合格にしない。
- 本書作成ではアプリコード、API、DBを変更していない。SSR細則の未決だけを分離し、スキル・素材・エリア／侵攻背景・日次／侵攻確定修正を止めない。
