## R06 既存実装と親の実接続確認対象

本体接続を限定照合した：

- `BattleView` は12秒の画像timeout/errorで再試行または「再生を終了する」へ進む。終了は現在result/imageKeyのerror時だけ有効で、同じresultの二度目をrefで抑止する。
- 通常出陣の `onComplete` は `QuestView` の `setPlaying(false)`。保存済みsettlementを結果表示する。
- 共闘/侵攻およびpending再開の `onComplete` は `RedesignApp` のbattle表示解除とread refresh。戦闘開始・報酬付与mutationを呼ばない。
- pending再開は保存 `pendingBattle.id` を同じrequestIdに指定し、quest/raidの元targetを再送する。これは画像終了ではなく別の既存再開経路。

これらは実装接続の確認であり、R06全体の受入ではない。従来の局所試験成功を再利用し、無目的な全量再実行はしていない。

親で実行する限定手順：

1. 非VIPの専用QAで元の戦闘requestId、開始/消費/報酬receiptを保存する。
2. 同一戦闘の必須画像1URLだけをerror/無応答とし、ロード停止→error→retry成功を確認する。mutation全体をofflineにしない。
3. 永続失敗では「再生を終了する」から出陣結果または共闘/侵攻へ復帰し、追加戦闘POSTがないこと、receipt・残高に二重消費/付与がないことを確認する。
4. 実pending状態の再読込では同じrequestIdの再開を行い、画像失敗/復帰後も元receiptと数量が一致することを確認する。

未検証：上記の実Preview画像故障表示、pending再開からの画像故障復帰、画像故障操作を含むreceipt照合。開始checkpointからの実API再開・同ID再送・receipt照合は下記追加検証で確認。担当のloopback通信検証とは分け、親が得た実証拠がある項目だけ追記して閉じる。

## R06 開始checkpointからの実API再開契約（追加準備）

親から実APIで閉じられる範囲の追加依頼を受け、`runBattle` とDB commit契約を照合した。[親用SQL template](r06-pending-fixture-template.sql)を親が専用QAに適用した（template自体は識別子未入力の保存用）。

その後、実認証APIのget_stateでpendingを取得し、同じrequestIdで再開・確定・再送する。`runBattle` はstartedの保存inputを再生計算し、`settlement:<元requestId>` 由来の固定UUIDで確定する。settledの同ID再送は保存resultを返す。これにより「開始保存checkpoint後の復帰・非重複」を検証できる。

このfixtureは**自然な通信切断やブラウザ画像障害を再現した証拠ではない**。R02のQA-B保存2戦は両方敗北なので、そのinputを使う場合は敗北結果・消費1回・報酬0維持の検証に限定し、勝利報酬の二重付与検証まで閉じない。後者は既存の勝利戦再送証拠と分けて扱う。
