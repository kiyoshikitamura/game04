## 3. 5画面の実装指示
### A. エリア一覧
各エリアに対応する既存マイページ背景を使う。画像を大きく見せ、名前・進捗の背後だけグラデーション等で可読性を確保する。
攻略中・解放済・未解放は、枠の角の旗やラベルアイコンで区別する。文字だけ、色だけに依存しない。クリア済の進捗も分かるようにする。
表示はクリア済・攻略中・解放済のエリアと、その先の次の未解放エリア1件まで。最終エリアまで最初から開示しない。実際の解放条件や進捗データは変更しない。
背景とエリアの対応は10エリアの既存設計に沿って記録し、同じ背景の仮流用が残っていないか確認する。

### B. ステージ一覧
エリア背景を活かし、ステージ番号の装飾、進行を感じる接続表現、枠、クリア・挑戦可能・未解放の差を付ける。モックの攻略ルート表現を参考にする。
背景のないテキストボックスの羅列で終わらせない。新しい分岐や進行条件は作らない。正式なステージ件数・名称・順序を使う。

### C. 挑戦前
主役は最終Waveのボス。既存バトル用ディフォルメ画像を大きく中央に見せ、背景・名前・属性バッジを合わせて構成する。
「Wave数：1」「消費行動力：3」の形式で、実データを読みやすく表示する。最初のWaveの登場人物を最終ボス扱いしない。
最終Waveに複数のボスがいる仕様なら、根拠なく1体に省略しない。
攻略のヒントはボタンに格納し、タップで内容を表示。報酬も「報酬を確認」ボタンに格納し、項目には既存アイテムアイコン・正式名称・数量等の正本情報を表示する。
属性は既存バッジ画像を使う。長い説明の常時表示は避ける。
モックの豊臣らしい画像や報酬は仮配置で、正式な登場・ドロップの承認ではない。
挑戦から出撃準備への既存遷移を保持する。

### D. 出撃準備
編成中の味方5人を主役にする。既存キャラ画像・レアリティ枠・属性バッジ・レアリティ表示を使い、装飾された配置番号を枠の左上等に置く。
モックで省略された名前も実装では表示する。名前・Lv・HPと各バッジの可読性を確保し、文字を小さくして押し込まない。
先に編成を確認できる構成にし、「編成変更」は編成表示より下へ置く。
「パーティ共通SP」はユーザー向けに「合計SP」と表記する。既存の共通SP400の意味・計算は変えず、各キャラのSPを新たに合算しない。
行動順や返却しない旨などの注意書きを常時大量に表示しない。必要な情報は適切な確認・ヘルプへ整理する。
「消費行動力3/50」のような重複表記は削除。消費量は挑戦前で明示し、不足時の回復導線は維持する。
キャラ詳細、編成変更、戻る、出撃の既存機能を保持する。

### E. キャラ詳細
キャラ画像を大きく使い、名前・レアリティ・属性・Lv・必要な能力値が確認できるようにする。
スキルは既存アイコンと正式な名称・消費SP・効果を接続する。内部の仮設定説明や不要な発動順の文章をユーザー画面へ出さない。
モックのスキル横3枠で文字が小さくなる場合は縦配置にする。既存のスキル枠数・装着状態を維持し、空き枠も区別する。
この詳細に未承認の編集機能を追加しない。戻った時の編成やスクロール状態を保持する。

## 4. データが反映されていない疑いの調査（ビジュアルと別管理）
発端は1-1の挑戦前に豊臣が表示されること。見た目で正誤を決めず、正式なエネミー・Wave・報酬Masterと表示経路を照合する。
以下を順に追跡し、食い違いが生じる箇所を特定する：
1. 正式Quest／Enemy／Reward／Skill MasterとPR #22の承認データ。
2. エリア・ステージID、Wave順、最終Wave・ボス判定、敵ID。
3. 敵IDから名前・属性・画像への対応、キャラ素材の割当。
4. API／Edge Function source・bundle、DBの実反映版、配信SHA。
5. QA固定データ、ハードコード、旧Master、fallback、キャッシュ。
6. 挑戦前表示と実際のバトル開始データが同じステージ・版を参照するか。
豊臣の魂報酬、キャラ詳細の仮スキル説明、旧70ステージ等の表示も同じ原因がないか確認する。
NEXT_PUBLIC_USE_MOCK_DB=falseだけで正式DBデータを使用していると断定しない。QAと実接続を区別して確認する。
原因・期待値・実値・参照元・修正箇所・反映先・未反映理由を表でGitに記録する。正式マスタに基づく接続不備は修正し、未特定値を独自補完しない。
DB／Edgeのdev反映が必要なら対象差分と確認項目を親の統合・配信担当へ渡す。接続修正と数値再設計を混同しない。
