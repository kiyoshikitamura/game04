## GAME04 Campaign / Acquisition

- RPCの `p_source=web_v1` はDB固定契約のため維持する。
- 分析軸 `utm_source=x/meta/organic/direct/unknown`、click ID優先順、初回Landing、TAP_TO_START、NAME_COMPLETED、Subject bindingはGAME03と同じ。
- 新規広告URLの `utm_campaign` は `game04_` から開始する。`utm_content` は素材slug。日付や公開日は自動設定しない。
- 捕捉した受信UTMは書き換えない。外部から来た値を忠実に記録し、GAME04専用DBで集計する。
- Journey token / landing metadata / Start marker / World intro pending events / MyPage context のsessionStorageキーを `game04_` に分離。GAME03キーの移入はしない。
- `supabaseUrl.ts` と `kpiRuntime.ts` のGAME04専用接続ガードを維持。GAME03 URL、本番環境への接続を拒否。
- DevとPreviewの計測は同一dev DBに入る。これらはリリース実績ではない。本番DBへQAのJourney・Subject・集計結果を移入しない。
- 広告出稿・X/Meta側のイベント送信・Pixel導入は今回実施しない。

URL作成例（広告公開はしない）:

```bash
node scripts/game04-campaign-url.mjs x qa character_a
node scripts/game04-campaign-url.mjs meta qa character_b
```

出力は既存GAME04 PreviewのLanding URL。第4引数でGAME04の別Preview originを指定可能。正式Domainは `config/game04-acquisition.json` の `productionOrigin=null` のまま。GAME03 URLへの生成は拒否する。

### 計測の確認順

1. X用またはMeta用URLでLanding到達。GAME04の `record_kpi_acquisition_landing_v1` が成功する。
2. 同一セッションで開始操作。`record_kpi_acquisition_observation_v1` に `TAP_TO_START` を送る。
3. 名前登録後に `NAME_COMPLETED`、本人のSubjectを `bind_kpi_acquisition_subject_v1` で紐付ける。
4. GAME04のKPIで source / campaign / creative 単位のLanding・Game Startを照合する。

今回のローカル最小確認はcampaign生成、X/Meta click ID、Direct、GAME03接続拒否のテストと既存Acquisition契約テスト。実広告からの計測確認・外部ブラウザ再訪・重複セッション等の総合QAは後工程。
